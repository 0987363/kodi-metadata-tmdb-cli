# 改造与验证结果

## 当前代码的处理链

CLI 必须通过 `--path` 指定一次现有媒体目录，递归发现后处理一次并退出。位置参数、重复 `--path` 和旧 `-mode` 参数会报错。`collector` 只保存目录名、文件名关键词和临时后缀的明确过滤设置；电影、剧集类型不由配置目录预设。

通用 LLM 对未预设类型的媒体每批最多 50 个进行分类与线索提取。程序校验路径覆盖、类型和节目归属，再组织电影或整剧任务，之后才应用人工来源、作品编号、季集、分组和映射约束。TMDb 使用官方 API，TheTVDB 使用公开搜索请求与 HTML；按 `scraper.providers` 顺序获取真实候选，每个有候选的来源对整剧任务判断一次，确认后停止后续来源。TMDb 与 TheTVDB 均已接入所需季集的来源批量取数。

全部适用来源正常完成仍无匹配时，`DescribeLocal` 仅根据输入路径返回标题、简介和分类，未知值留空；电影、节目和单集的 `local` 身份由程序生成，不冒充网站编号或来源页面。来源 HTTP、协议、鉴权等错误直接失败，人工明确指定的作品未找到或未被确认也不触发本地整理。

`llms` 保存独立模型实例，`scraper` 保存任务引用、来源顺序、缓存与输出开关；模型名称、判断器及连接参数的既有契约保持不变。来源在内存中的快照只在一次 CLI 生命周期内复用；`scraper.cache_hours` 控制跨次运行的磁盘响应缓存，`0` 禁用磁盘复用。整剧批量结果采用独立的 `series-*` 缓存命名空间，无需仅为批量处理统一提高旧响应封装版本。

搜索按标题变体收集完整分页，缺失、矛盾、无进展或超限均报错；单查询原始条数及合并候选均最多 254。已删除 Kodi JSON-RPC、ffmpeg/ffprobe、音乐视频、旧规则解析、监听和定时扫描。原盘处理、人工约束及有限来源重试保留。更完整的配置和流程见 [设计与契约](metadata-providers.md)。

## NFO 与文件输出

电影和单集只写来源提供的正数分钟时长；无效语言标签和网站总季集数不写入 NFO，零季及明确季集坐标保留。对象自身网站编号与网站确认的同对象跨站编号保留，不把父节目编号复制给单集。本地整理只输出受输入支持的字段和程序生成的本地身份，不生成来源图片。

普通电影 Logo 使用与视频同名前缀的 `-logo.png`，NFO 保留 clearlogo 来源 URL。原盘在电影根目录和索引位置写相同元数据；单文件原子替换不代表整组文件事务回滚。四端官方文档与源码核查及其边界见 [专项报告](nfo-recognition-audit.md)。

## 历史验证与当前待验收范围

初始改造曾用受控模型和来源服务，从配置文件启动 CLI，验证具名模型、来源顺序、分页、缓存、NFO 与路径，并完成 race、vet 和多平台构建。该记录只证明当时的初始实现；不能用当时的测试计数声称当前工作树的一次性 CLI、AI 分类、整剧批量取数和本地整理已完成最终回归。

当前这些功能已写入代码，主分支完整 race、vet 和四个平台构建已通过。`res.txt` 固定 10 部节目与 `res2.txt` 新集合的实际样本运行也仍待完成；两个文件名仅是验收输入清单，不参与生产分类规则或提示词特例。受控 HTTP 回放不证明用户真实模型对媒体库的判断准确率，也不证明实际来源网络可达。

Kodi、Jellyfin、Emby、Silo Server 的读取契约采用官方文档与源码核查，尚未执行四端真实服务器导入。部署网络与真实 TMDb 凭据仍需按实际环境验收；不能把静态文档核查或空视频输出检查视为播放能力验证。
